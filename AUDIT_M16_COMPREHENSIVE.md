## Executive Summary

UPCP is a well-structured modular monolith with strong foundations: DDD bounded contexts, TDD discipline, JWT auth, structured logging, and a polished UI. The M15 Agent Workflow milestone was delivered cleanly. The M16 (Notifications & Reporting) work has **Sprint 1 partially done** — the `NotificationTrigger` service is implemented and wired into 6 workflow events, but Sprints 2-4 (channels, analytics, frontend) are entirely pending.

**Stability: GOOD** — 965 tests pass, no flaky tests observed.
**Reliability: GOOD** — Proper error handling, stale reaper, lifecycle state machine.
**Quality: GOOD with gaps** — Clean code, but `as any` in tests, Settings page version hardcoded.
**UX: GOOD foundation, needs polish** — Strong component library, but missing analytics, settings are thin.
**Architecture: SOLID** — Clean DDD boundaries, no cross-context violations found.

### 3.2 Architecture Issues

| # | Severity | Finding | Detail |
|---|----------|---------|--------|
| A1 | **High** | `NotificationTrigger` is instantiated ad-hoc in 6 places with `try/except: pass` | Should be injected as a dependency or use an event bus pattern. Current approach means: (1) each caller must remember to import+instantiate, (2) errors are invisible, (3) no retry mechanism. |

| A3 | **Medium** | `NotificationChannel` and `NotificationDelivery` models not yet created (TASK-0101 PENDING) | The notification system is fire-and-forget with no delivery tracking. |

| A7 | **Medium** | Dead `auth/` module from earlier iteration | `backend/app/auth/` contains unused `rbac_user`, `rbac_role`, `rbac_permission` tables. Active auth is in `identity/`. Should be removed. |
| A8 | **Low** | `app/shared/config.py` uses `lru_cache` for settings singleton | Fine for production but makes testing harder — env var changes after first import are ignored. |

## 9. STRONGER REWORK RECOMMENDATIONS

### 9.1 Notification System Architecture (Rework Needed)

**Current:** Direct service-to-trigger calls with `try/except: pass`.

**Recommended:** Event-driven architecture with domain events.

```
Service → emit DomainEvent → EventBus → [NotificationTrigger, AuditLogger, AnalyticsCollector]
```

**Benefits:**
- Decoupled — producers don't know about consumers
- Testable — can test event emission independently
- Extensible — add new consumers without modifying producers
- Observable — can log all events for debugging

**Implementation:**
1. Create `shared/events.py` with `DomainEvent` base class and `EventBus`
2. Services emit events instead of calling triggers directly
3. `NotificationTrigger` subscribes to relevant events
4. Future: `AnalyticsCollector` subscribes to same events

### 9.2 Settings Architecture (Rework Recommended)

**Current:** Single-page Settings with 3 cards (theme, API info, version).

**Recommended:** Tabbed settings with proper separation.

```
/settings
├── Profile        — user name, email, avatar, password change
├── Notifications  — per-event-type toggle, channel selection
├── Channels       — email/webhook CRUD, test connection
├── Organization   — members, roles, billing (future)
├── Appearance     — theme, language (future)
└── About          — version, API info, health
```

### 9.3 Dashboard Architecture (Enhancement Recommended)

**Current:** Global dashboard with stats, attention cards, activity feed, recent projects.

**Recommended:** Two-tier dashboard system.

```
/ (Global Dashboard)
├── Stats row (projects, tasks, attention)
├── Attention sections (7 categories)
├── Activity feed + agent summary
└── Recent projects

/projects/:id (Project Dashboard)
├── Health score + trend chart
├── Task completion donut chart
├── Velocity chart (tasks/week)
├── Agent activity for this project
├── Recent changes for this project
└── Quality gate status
```

### 9.4 Analytics Architecture (Design for M16 S3/S4)

**Recommended:** Analytics as a read-optimized CQRS projection.

```
Write path: Services → Domain Events
Read path: AnalyticsService → materialized views / aggregation queries

Charts:
- Line chart: task completion over time (7/30/90 days)
- Bar chart: velocity per week
- Donut chart: task status distribution
- Table: agent performance metrics
- Sparkline: health score trend
```
